# ۰۱ — معماری و انتخاب تکنولوژی

### چرا نه Go / نه .NET / نه بازنویسی

بازنویسی ۲۳ هزار خط کدِ تست‌شده با Go هیچ چیزی برای کاربر عوض نمی‌کند و ۳ تا ۴ هفته وقت می‌برد.
گلوگاه این محصول **نقدینگی بازار** است (تعداد آگهی و خریدار در بانه)، نه توان پردازشی سرور.
Node در یک VPS دو هسته‌ای با ۴۰۰۰ درخواست در دقیقه راحت نفس می‌کشد؛ این محصول در اوجش به یک
هزارم آن هم نمی‌رسد. اگر روزی لازم شد، مسیر مهاجرت در بخش ۶ آماده است.

### چرا Capacitor و نه Flutter

درخواست مالک: «اندروید نصب بشه، iPhone تحت وب». نسخهٔ ۱ یک PWA کامل است (Service Worker، آیکون،
manifest). Capacitor همان PWA را در یک پوستهٔ نیتیو می‌گذارد و APK واقعی می‌دهد، با دسترسی به
Geolocation نیتیو، FCM و دوربین — بدون نوشتن دوبارهٔ رابط کاربری. هزینه: حدود ۲ روز در مقابل
۳ تا ۴ هفته برای Flutter. اگر بعداً انیمیشن سنگین یا نقشهٔ نیتیو لازم شد، مسیر Flutter باز است.

## ۲. توپولوژی استقرار (فاز ۱)

```
                    ┌──────────────┐
   اینترنت  ───────▶│  Caddy :443  │  گواهی خودکار، HSTS
                    └──────┬───────┘
             ┌─────────────┼──────────────┐
             ▼             ▼              ▼
      /         apps/web  /admin    /v1 → api:3000
                                            │
                                   ┌────────┴─────────┐
                                   ▼                  ▼
                             Postgres 16          کارگر انقضا
                             (+PostGIS)        (همان ایمیج، دستور جدا)
```

- سه کانتینر: `api`, `web`, `admin` + `db` + `caddy` + `worker`.
- کارگر انقضا **همان کد API** است با `ENTRYPOINT node dist/worker.js`؛ ایمیج اضافه لازم نیست.
- همهٔ داده‌ها روی volume؛ `pg_dump` شبانه به فضای ابری.

## ۴. اندازهٔ سرور و هزینه

| مرحله                                         | منابع                                  | هزینهٔ تقریبی ماهانه |
| --------------------------------------------- | -------------------------------------- | ------------------- |
| اجرا در بانه (تا ~۲٬۰۰۰ کاربر، ۲۰۰ آگهی فعال) | ۲ vCPU / ۴ GB / ۶۰ GB SSD              | ~۱۰ تا ۱۵ دلار      |
| رشد به ۲۰ هزار کاربر                          | ۴ vCPU / ۸ GB + PgBouncer              | ~۳۰ دلار            |
| چند شهر                                       | ۲ نمونهٔ API + Postgres managed + Redis | ~۸۰ دلار به بالا    |

مصرف واقعی پایین است چون: بار پردازشی روی گوشی است (کلاینت SPA/APK)، تصویر و ویدیو در اپ نیست،
و سنگین‌ترین کوئری یک `SELECT` روی ایندکس مکانی است.

## ۵. تصمیم‌های فنی که باید در کد رعایت شود

1. **رزرو اتمی در SQL**، نه `if (order.status === 'OPEN')`. جزئیات در `02-DATA-MODEL.md`.
2. **زمان‌بند تنها منبع انقضا**. هیچ بررسی «هنگام باز شدن اپ» به‌عنوان راه‌حل اصلی نباشد؛
   حداکثر به‌عنوان نمایش «این سفارش منقضی است» با خواندن وضعیت واقعی.
3. **`KeyedLock` درون‌پروسه‌ای کافی نیست** — کنارش قید دیتابیسی لازم است (نسخهٔ ۱ خودش در
   `docs/ASSUMPTIONS.md` این را نوشته و انجام نداده).
4. **همهٔ زمان‌ها UTC در دیتابیس**، نمایش به وقت تهران (`Asia/Tehran`) در UI.
5. **مبلغ‌ها عدد صحیح تومان** (بدون اعشار، `bigint`). هیچ‌جا `float` برای پول.
6. **شناسه‌ها UUIDv7** یا `bigserial`؛ نسخهٔ ۱ UUID دارد، همان می‌ماند.
7. **پول و قیمت هرگز در کلاینت محاسبه نشود**؛ کلاینت فقط نمایش می‌دهد.
8. **API نسخه‌دار** (`/v1`) و تغییر ناسازگار = `/v2`.
9. **همهٔ رویدادهای پول‌ساز در `audit_log`** ثبت شوند (تأیید پرداخت، تعلیق، تغییر پلن).
10. **پیکربندی از دیتابیس، نه از کد**: انقضا، پلن‌ها، روش پرداخت، متن پیامک، منطقه‌ها.

## ۶. مسیر مقیاس (وقتی لازم شد)

| نشانه                   | کار                                                         |
| ----------------------- | ----------------------------------------------------------- |
| CPU API > ۷۰٪ پایدار    | نمونهٔ دوم API + Caddy `lb_policy`                           |
| چند نمونهٔ API           | Redis برای PubSub چت و سوکت‌ها + PgBouncer                  |
| کوئری مکان کند          | ایندکس GiST + materialized view برای شمارش بازار            |
| نوشتن زیاد روی سفارش‌ها | پارتیشن‌بندی `orders` بر اساس ماه                           |
| شهرهای متعدد            | افزودن `zone_id` به کلیدهای کش و در نهایت shard بر اساس شهر |

هیچ‌کدام از این‌ها امروز لازم نیست؛ اگر از روز اول Redis و Kubernetes بگذاریم، فقط هزینه و
پیچیدگی اضافه کرده‌ایم.

## ۷. چیزهایی که آگاهانه انتخاب نشده‌اند

- **میکروسرویس**: یک API کافی است.
- **Kubernetes**: یک VPS + Compose جواب می‌دهد.
- **اپ نیتیو کاتلین جداگانه**: Capacitor همان نتیجه را با یک‌دهم هزینه می‌دهد.
- **GraphQL**: REST نسخه‌بندی‌شده ساده‌تر و برای این دامنه کافی است.
- **پرداخت درون‌برنامه‌ای بین دو کاربر**: مدل کسب‌وکار بر اشتراک است، نه کارمزد معامله؛ از
  پیچیدگی مالی و حقوقی آن دوری می‌کنیم.
