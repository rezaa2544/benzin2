# G-14 — پنل پیامک

**پذیرش:** زنجیرهٔ ارائه‌دهنده (sms.ir → کاوه‌نگار → console) با failover؛ کلید و الگوها از پنل؛
دکمهٔ «ارسال آزمایشی» با نمایش پاسخ واقعی سرویس.

پیش از این تسک، زنجیره یک‌بار در زمان بوت از متغیرهای محیطی ساخته می‌شد: عوض‌کردن کلید یعنی ویرایش
`.env` و راه‌اندازی مجدد، و دکمهٔ آزمایش هم هر پاسخی را «ارسال شد» می‌خواند. حالا زنجیره در زمان
اجرا از ردیف‌های `provider_settings` خوانده می‌شود و آزمایش، جواب خودِ سرویس را نشان می‌دهد.

## ۱) زنجیره

`GET /v1/admin/sms`:

```json
{
  "enabled": true,
  "source": "PANEL",
  "otpMessage": "کد ورود شما به بنزین: {code}",
  "chain": [
    {
      "provider": "smsir",
      "priority": 5,
      "isActive": true,
      "keySet": true,
      "sender": "30007732",
      "template": "12345"
    },
    {
      "provider": "default",
      "priority": 0,
      "isActive": true,
      "keySet": true,
      "sender": null,
      "template": null
    }
  ],
  "lastAttempts": []
}
```

- `source` سه حالت دارد: `PANEL` (حداقل یک ارائه‌دهندهٔ فعال و کامل در پنل)، `ENV` (هیچ ردیف
  قابل‌استفاده‌ای نیست، پس همان زنجیرهٔ متغیرهای محیط کار می‌کند) و `CONSOLE`.
- `chain` به ترتیب **اولویت نزولی** است و **آخرین حلقه همیشه `default`** است: زنجیرهٔ محیطی که
  پیش از این تسک وجود داشت. یعنی خرابی همهٔ ارائه‌دهنده‌های پنل، ارسال را قطع نمی‌کند؛ به همان
  مسیر قبلی برمی‌گردد و در گزارش تلاش‌ها دیده می‌شود.
- کلید هرگز برنمی‌گردد؛ فقط `keySet: true|false`. تصمیم در سرویس گرفته می‌شود، نه در فرم.
- ردیف غیرفعال در فهرست می‌آید (تا مالک ببیندش) ولی هیچ transportی نمی‌سازد.

**ثبت بدون راه‌اندازی مجدد:** زنجیره cache می‌شود و `PUT /v1/admin/providers` با
`kind = SMS` آن را باطل می‌کند. تست
«takes a saved key into service without a restart» همین را می‌سنجد: `source` پیش از ذخیره `ENV`
است و بلافاصله بعد از آن `PANEL`.

## ۲) الگوها

| کلید                           | معنا                                      |
| ------------------------------ | ----------------------------------------- |
| `config.priority`              | عدد بزرگ‌تر زودتر امتحان می‌شود           |
| `config.sender`                | شمارهٔ خط فرستنده                          |
| `config.template`              | شناسهٔ الگوی sms.ir / نام الگوی کاوه‌نگار  |
| `config.templateParameter`     | نام پارامتر کد در sms.ir (پیش‌فرض `code`) |
| `notification.sms_otp_message` | متن پیامک کد ورود، با `{code}`            |

- اگر ارائه‌دهنده الگو داشته باشد، کد از مسیر `sendCode` (verify/lookup) می‌رود و متن آزاد
  فرستاده نمی‌شود؛ بدون الگو، همان متن `notification.sms_otp_message` با `{code}` جایگزین می‌شود.
- تنظیم `notification.sms_otp_message` **بدون** `{code}` با ۴۲۲ رد می‌شود
  (`OTP_TEMPLATE_MISSING_CODE`). پیامکی که کد نداشته باشد، ارسال‌شده به نظر می‌رسد و بی‌فایده است —
  پس اعتبارسنجی در سطح تنظیمات است، نه در لحظهٔ ارسال.

## ۳) «ارسال آزمایشی»

`POST /v1/admin/sms/test` با بدنهٔ `{ phone, provider? }`:

```json
{
  "delivered": true,
  "message": "پیام آزمایشی بنزین: تنظیمات پنل پیامک درست است.",
  "attempts": [
    {
      "provider": "smsir",
      "ok": false,
      "status": 200,
      "mode": "text",
      "error": "rejected by provider",
      "raw": "{\"status\":0,\"message\":\"line is disabled\"}"
    },
    {
      "provider": "kavenegar",
      "ok": true,
      "status": null,
      "mode": "text",
      "raw": "{\"return\":{\"status\":200,\"message\":\"ok\"}}"
    }
  ]
}
```

- **بدون `provider`** (یا `"auto"`) کل زنجیره امتحان می‌شود؛ یعنی خودِ failover آزمایش می‌شود.
- **با نام یک ارائه‌دهنده** فقط همان حلقه، تا خرابی حلقهٔ دوم بدون خاموش‌کردن حلقهٔ اول دیده شود.
- `raw` پاسخ خودِ سرویس است (بدنهٔ HTTP، trim‌شده) و در UI بدون بازنویسی چاپ می‌شود. برای شکست هم
  `raw` می‌آید — `SmsTransportError` بدنه را نگه می‌دارد.
- ۲۰۰ برمی‌گردد حتی وقتی `delivered = false`؛ «نرسید» یک نتیجهٔ معتبر آزمایش است، نه خطای سرور.
  کد خطای عمومی ۵۰۲ قدیمی (`PROVIDER_TEST_FAILED`) حذف شد چون پیام سرویس را پنهان می‌کرد.
- هر آزمایش در audit با `sms.tested` ثبت می‌شود (provider، phone، delivered، خلاصهٔ تلاش‌ها).

## ۴) رابط

`/sms` در پنل:

- کارت «زنجیرهٔ ارسال»: هر حلقه با اولویت، وضعیت، خط، الگو و «کلید ثبت شده / کلید ندارد»؛ منبع
  تنظیمات (`پنل` / `متغیرهای محیط`) بالای کارت.
- جدول ارائه‌دهنده‌ها با ستون‌های اولویت و الگو؛ فرم ویرایش، کلید، خط، اولویت، الگو و نام پارامتر
  را می‌گیرد.
- کارت «ارسال آزمایشی»: شماره + انتخاب «کل زنجیره (با failover)» یا یک ارائه‌دهنده؛ نتیجه با
  جدول تلاش‌ها (ارائه‌دهنده، موفق/ناموفق، کد وضعیت، حالت، **پاسخ واقعی سرویس**).
- متن پیامک کد ورود با راهنمای «باید شامل {code} باشد» و دکمهٔ ذخیره که تا وجود `{code}` فعال
  نمی‌شود.

## ۵) تست‌ها

- `apps/api/test/g14-sms-panel.test.ts` (۸ تست): ترتیب و منبع زنجیره، پنهان‌ماندن کلید، failover با
  رد شدن ارائه‌دهندهٔ اول، نادیده‌گرفتن ردیف غیرفعال، متن کد از پنل و رد متن بدون `{code}`، گزارش
  صادقانه وقتی همه خرابند، اعمال کلید بدون restart + audit، و محدود بودن پنل به کارکنان.
- `apps/admin/test/sms-panel.test.ts` (۵ تست): ترتیب زنجیره در UI (اولویت نزولی، `default` آخر،
  بدون mutation) و رنگ/متن گزارش تلاش.
- تست‌های API با `smsFetch` تزریقی کار می‌کنند؛ `offlineSmsFetch` در `test/helpers.ts` هر درخواست
  را فوراً رد می‌کند تا هیچ تستی به شبکه نزند.
- smoke: سه گام تازه — شکل زنجیره، ارسال آزمایشی روی `console` با `raw`، و ۴۲۲ برای شمارهٔ بد.

## ۶) نکتهٔ عملیاتی

`SMS_PROVIDERS` و کلیدهای محیطی حذف نشدند: آن‌ها **پیش‌فرض بوت** و حلقهٔ `default` هستند. یعنی نصب
تازه بدون هیچ تنظیمی کار می‌کند، و هر چه در پنل تعریف شود بالاتر از آن می‌نشیند. برای اینکه پنل
تنها منبع شود، کافی است ارائه‌دهنده‌های پنل را فعال کنید و `SMS_PROVIDERS` را خالی بگذارید.
