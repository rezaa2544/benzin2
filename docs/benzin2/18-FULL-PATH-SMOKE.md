# G-22 — تست دود مسیر کامل

**پذیرش:** یک اسکریپت که با API واقعی این مسیر را اجرا کند: ثبت‌نام خریدار و فروشنده → ثبت آگهی →
خرید اشتراک (کارت‌به‌کارت review) → رزرو → تأیید فروشنده → کد تحویل → COMPLETED → بررسی
`audit_log`. اگر این تست سبز شد، «برنامه به مرحلهٔ اجرا رسیده» است.

`scripts/smoke-api.mjs` از پیش بیشتر بازار را می‌پیمود، ولی سه چیز را جا می‌انداخت و همین‌ها دقیقاً
چیزهایی‌اند که «آماده برای اجرا» را می‌سازند: **پول**، **چرخهٔ کامل رزرو با دو حساب تازه** و
**دفتر audit**. اسکریپت تازه `scripts/smoke-happy-path.mjs` آن‌ها را کنار هم می‌گذارد و از حساب‌های
مشترکِ دمو استفاده نمی‌کند: هر اجرا دو کاربر واقعاً تازه می‌سازد.

## اجرا

```bash
# روی اپ نصب‌شده (منفذ 41721)
node scripts/smoke-happy-path.mjs

# روی سرور توسعه (منفذ 4301)
API=http://127.0.0.1:4301 node scripts/smoke-happy-path.mjs
```

`pnpm smoke:happy` هم همین کار را می‌کند. کد خروج صفر یعنی همهٔ ۲۵ گام سبز؛ هر گام شکست‌خورده در
فهرست پایانی چاپ می‌شود و کد خروج ۱ برمی‌گردد.

دو چیز لازم دارد:

| متغیر | پیش‌فرض | چرا |
|---|---|---|
| `SMOKE_OPERATOR` | `09187888993` | اپراتور برای عوض‌کردن حالت کارت، تأیید واریز و خواندن audit |
| `SMOKE_OTP` | `12345` | کد ثابت توسعه؛ API باید `DEV_FIXED_OTP` را ست کرده باشد |

شمارهٔ هر دو حساب تازه در هر اجرا ساخته می‌شود (`0901…` خریدار، `0902…` فروشنده، با پسوند
تصادفی)، پس اسکریپت روی همان دیتابیس چند بار قابل اجراست و چیزی برای پاک‌کردن باقی نمی‌گذارد.

## چه چیزی را ثابت می‌کند

| # | گام | ادعایی که قفل می‌شود |
|---|---|---|
| ۱ | `healthz` | سرور بالاست (اگر نه، اجرا همان‌جا با کد ۱ می‌ایستد) |
| ۲ | ورود اپراتور | حساب اپراتور واقعاً `OWNER`/`ADMIN` است |
| ۳ | `payment.card_mode` → `review` | نوشتن تنظیم + **خواندن دوباره** تا معلوم شود ماندگار است |
| ۴ | ثبت‌نام خریدار و فروشنده | `isNewUser` برای هر دو درست است، و کاربر تازه با پلن رایگان بالا می‌آید |
| ۵ | ثبت آگهی ۶۰ لیتری | `201` و `OPEN`؛ اگر نقطهٔ جغرافیایی در ناحیهٔ دیگری باشد، `ZONE_MISMATCH` را می‌پذیرد و بدون نقطه آگهی می‌گذارد |
| ۶ | دیدن آگهی در بازار | آگهی تازه در فهرست خریدار هست و کارت آن نشان پاسخ‌دهی دارد |
| ۷ | فاکتور اشتراک | `PENDING`, کارت مقصد، مبلغ یکتا بزرگ‌تر از مبلغ پلن، دستور پرداخت فارسی |
| ۸ | ارسال شمارهٔ پیگیری | `NEEDS_REVIEW` + `queued` — یعنی حالت review واقعاً فعال است |
| ۹ | صف اپراتور | همان فاکتور در `GET /v1/admin/payments?status=NEEDS_REVIEW` دیده می‌شود |
| ۱۰ | تأیید اپراتور | پرداخت `PAID` **و** اشتراک در همان درخواست `ACTIVE` می‌شود |
| ۱۱ | `GET /v1/me/entitlements` و `/v1/me/subscription` | `source=SUBSCRIPTION`، `phoneVisible=true`، `remaining=null` |
| ۱۲ | تأیید دوباره | `409 PAYMENT_ALREADY_SETTLED` — پول دوبار ثبت نمی‌شود |
| ۱۳ | `POST /v1/admin/reconciliation` | کار شبانه چیزی برای ترمیم پیدا نمی‌کند (`healedPayments=0`) |
| ۱۴ | رزرو و تأیید فروشنده | `PENDING_OWNER` → `CONFIRMED` |
| ۱۵ | شمارِ طرف مقابل | خریدارِ پول‌داده شماره را می‌گیرد، فروشندهٔ پلن‌رایگان `402 PHONE_REQUIRES_SUBSCRIPTION` |
| ۱۶ | کد تحویل | چهاررقمی، فقط برای خریدار؛ فروشنده `403` |
| ۱۷ | COMPLETE با کد | `COMPLETED`، سفارش هم `COMPLETED`، رزرو در «معامله‌های من» دیده می‌شود |
| ۱۸ | امتیاز | ۵ ستاره ثبت می‌شود |
| ۱۹ | `GET /v1/admin/audit` | هر نُه اقدام کلیدی مسیر موجود است و `payment.paid` به **اپراتور** نسبت داده شده، نه به خریدار |
| ۲۰ | فیلتر audit | ردیف‌های همین رزرو جدا قابل بازخوانی‌اند |
| ۲۱ | برگشت حالت کارت | تنظیم به مقدار پیش از اجرا برمی‌گردد و بازخوانی تأییدش می‌کند |

گام‌های ۳ و ۲۱ با هم یعنی اسکریپت روی سرور مشترک بی‌خیال نیست: سرور را در حالتی که پیدایش کرده
رها نمی‌کند. (اگر اجرا پیش از گام آخر بترکد، تنظیم روی `review` می‌ماند؛ گام بعدی همان مقدار را
«قبلی» می‌گیرد و برمی‌گرداند، پس اجرای بعدی هم خودش را درست می‌کند.)

## چرا این مسیر، و نه مسیر درگاه

درگاه بانکی (G-12) به feed واقعی بانک و callback مرورگر نیاز دارد؛ برای «مسیر کامل» چیزی که
می‌شود روی هر نصب تازه‌ای تکرار کرد همان کارت‌به‌کارت با تأیید انسان است: خریدار واریز می‌کند،
شمارهٔ پیگیری می‌فرستد، اپراتور تأیید می‌کند و همان مسیر `settle` اشتراک را فعال می‌کند. درگاه در
`smoke-api.mjs` جداگانه تست می‌شود (`POST /v1/payments/gateway/callback` → `302`).

## نتیجهٔ اجرا

- روی سرور توسعه (حافظه‌ای، `NODE_ENV=development`، منفذ 4301): **۲۵/۲۵**.
- روی اپ نصب‌شده (`C:\Program Files\Benzin2`، Postgres، منفذ 41721): **۲۵/۲۵**، کد خروج ۰.
  در آن اجرا حالت کارت پیش از تست `auto` بود، اسکریپت آن را `review` کرد و در پایان به `auto`
  برگرداند؛ در همان اجرا فاکتور ۴۹٬۰۱۳ تومانی با شمارهٔ پیگیری `HAPPY-…` تأیید شد و معامله با کد
  تحویل بسته شد.

## نگه‌داشتنش سبز

این اسکریپت پایان‌به‌پایان است، پس هر تغییر در قرارداد API می‌تواند آن را بشکند — که همان هدف
است. اگر شرکتی تازه («کارمزد»، «کد تخفیف») به مسیر خرید اضافه شد، گام مربوط به فاکتور همان‌جاست که
باید به‌روز شود؛ و اگر اقدام تازه‌ای در audit اضافه شد، فهرست `required` در گام ۱۹.
