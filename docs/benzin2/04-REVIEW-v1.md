## ۳. سه نقص ساختاری دیگر

### ۳.۱ رزرو، اتمی در سطح دیتابیس نیست

`modules/keyed-lock.ts` یک mutex درون‌پروسه‌ای است و خودش در کامنت نوشته:

> Scope: one process. A multi-instance deployment needs the matching database constraint as well
> (see docs/ASSUMPTIONS.md A34) — the lock is the cheap half, the constraint is the durable half.

آن «نیمهٔ دوم» ساخته نشده: نه `update ... where status='OPEN'` در SQL دیده می‌شود، نه قید یکتایی.
با دو نمونهٔ API، دو خریدار می‌توانند یک آگهی را بگیرند. الزام مالک («رزرو را اتمی کن») برآورده نشده.

### ۳.۲ انقضا با کارگر زمان‌بند نیست

تنها `setInterval` موجود، heartbeat سوکت چت است. انقضای رزرو/آگهی هنگام خواندن چک می‌شود.
پیامدهای واقعی:
- آگهی منقضی در فهرست می‌ماند.
- رزروِ رهاشده هرگز آزاد نمی‌شود، پس آگهی برای بقیه قفل می‌ماند.
- اعلان «رزرو شما به‌خاطر بی‌پاسخی لغو شد» و «آگهی‌ات ۶ ساعت دیگر تمام می‌شود» فرستاده نمی‌شود،
  چون هیچ رویدادی وجود ندارد که آن‌ها را راه بیندازد.

### ۳.۳ کارت‌به‌کارت واقعاً تأیید نمی‌شود

```ts
// payment-providers.ts
export class CardToCardProvider implements PaymentProvider {
  readonly kind = 'CARD_TO_CARD' as const;
  ...
  return { ok: false, reference: null, reason: 'MANUAL_REVIEW' };
```

یعنی همیشه «در انتظار بررسی» — که با صف تأیید دستی در پنل کار می‌کند، ولی خودکار نیست. درگاه
زرین‌پال پیاده شده (`ZarinpalGatewayProvider`, `payment.zarinpal.com`) اما در محیط سندباکس است و
برای production به دامنه/آی‌پی ثابت و مرچنت واقعی نیاز دارد.

## ۵. بدهی فنی کوچک‌تر

- **۱۴ شاخهٔ `arena/*`** در مخزن باقی مانده؛ باید پاک شوند تا آرنا گم نشود.
- چند ناهماهنگی نام‌گذاری در مستندات خودِ مخزن (`E2` در main.ts، `E2-02` در README، `F-01` در نوتیشن)
  برای یک کار. تسک‌ها باید یک شناسهٔ واحد داشته باشند؛ از این پس `G-xx`.
- `Dockerfile` در ریشه نیست (در `infra/`) — برای Compose مشکلی نیست، برای آرنا گمراه‌کننده است.
- هیچ‌جا `healthz` سبک برای liveness نیست؛ Caddy فقط پروکسی می‌کند.
- تست‌ها زیادند (۵۲ فایل) ولی هیچ‌کدام روی Postgres واقعی اجرا نمی‌شوند؛ تست یکپارچهٔ «دو رزرو
  هم‌زمان» وجود ندارد و باید نوشته شود (بدون آن، G-02 قابل اثبات نیست).
