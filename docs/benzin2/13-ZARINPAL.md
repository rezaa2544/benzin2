# G-12 — زرین‌پال production + آشتی تراکنش

**پذیرش:** چرخهٔ کامل request/verify، callback روی دامنهٔ HTTPS، تلاش مجدد بررسی سه‌باره توسط کارگر،
گزارش درآمد. کلید واقعی فقط در `.env` سرور، هرگز در مخزن.

این سند می‌گوید پول آنلاین چطور وارد می‌شود، چرا حتی وقتی مرورگر خریدار بسته می‌شود پول گم نمی‌شود،
و برای فعال‌کردن درگاه واقعی دقیقاً چه چیزی باید روی سرور ست شود. کد از روز اول با فرمت واقعی زرین‌پال
حرف می‌زند؛ فقط کلید مرچنت است که در این محیط نیست.

## ۱) چرخهٔ پرداخت

```
POST /v1/subscriptions {method: GATEWAY}
   └─ ZarinpalGatewayProvider.init
        POST https://payment.zarinpal.com/pg/v4/payment/request.json
             { merchant_id, amount: تومان×۱۰ (ریال), callback_url, description }
        ← { data: { code: 100, authority } }
   ← redirectUrl = https://payment.zarinpal.com/pg/StartPay/<authority>

خریدار در درگاه بانک پرداخت می‌کند
   └─ زرین‌پال مرورگر را برمی‌گرداند:  GET <callback_url>?Authority=…&Status=OK|NOK
        ├─ Status=NOK   → فاکتور FAILED با مرجع GATEWAY_CANCELLED (لغو، نه خطا)
        ├─ Status=OK    → POST …/verify.json { merchant_id, amount, authority }
        │                   ├─ code 100 → PAID + فعال‌سازی اشتراک
        │                   ├─ code 101 → همان (قبلاً verify شده؛ رفرش صفحه دوبار پول نمی‌گیرد)
        │                   └─ خطای شبکه/۵xx → تلاش بعدی توسط کارگر
        └─ نتیجه به‌صورت ۳۰۲ به اپ برمی‌گردد: /plans?payment=paid|failed|pending|unknown
```

مبلغ همیشه در ریال به بانک می‌رود و در تومان در سامانه می‌ماند؛ این تبدیل **فقط** یک‌جا، در
`payment-providers.ts`، انجام می‌شود.

## ۲) چرا پول گم نمی‌شود

callback در مرورگر خریدار است: تب بسته می‌شود، اینترنت قطع می‌شود، یا خود verify به ۵۰۲ می‌خورد.
سه لایه این را می‌پوشانند:

1. **زمان ساخت فاکتور:** برای هر فاکتور درگاهی، اولین بررسی دو دقیقه بعد در صف کارگر گذاشته می‌شود
   (`next_verify_at`)؛ یعنی حتی اگر callback هیچ‌وقت نرسد، خود سامانه از بانک می‌پرسد.
2. **تلاش مجدد:** هر شکست گذرا (خطای شبکه) یک تلاش به `verify_attempts` اضافه می‌کند و زمان بعدی را
   با فاصلهٔ فزاینده (`payment.verify_retry_minutes` × شمارهٔ تلاش) می‌گذارد. پیش‌فرض: **۳ تلاش**.
3. **بازبینی انسانی:** با تمام‌شدن بودجه، فاکتور به `NEEDS_REVIEW` می‌رود (نه `EXPIRED`)،
   آدیت `payment.verify_exhausted` ثبت می‌شود و به خریدار اعلان `PAYMENT_NEEDS_REVIEW` می‌رود؛
   اپراتور با همان صف G-11 تأیید یا رد می‌کند.

نکتهٔ مهم: پاسخی که بانک *داده* (کد خطا مثل `-51`) شکست قطعی است و همان‌جا `FAILED` می‌شود؛ فقط
خطای گذرا (throw/شبکه) وارد صف تلاش مجدد می‌شود. «تلاش مجدد روی یک رد قطعی» فقط تأخیر در پاسخ به
خریدار است.

## ۳) پیکربندی روی سرور (کلید هرگز در مخزن)

| متغیر | نمونه | توضیح |
|---|---|---|
| `PAYMENT_GATEWAY` | `zarinpal` | `sandbox` (پیش‌فرض توسعه) یا `zarinpal` |
| `ZARINPAL_MERCHANT_ID` | ۳۶ کاراکتر از پنل زرین‌پال | فقط در `.env` سرور |
| `ZARINPAL_BASE_URL` | `https://payment.zarinpal.com` | برای تست مقابل سندباکس زرین‌پال تغییر می‌کند |
| `PAYMENT_CALLBACK_URL` | `https://app.benzin.ir/v1/payments/gateway/callback` | باید HTTPS باشد |
| `PAYMENT_RETURN_URL` | `https://app.benzin.ir/plans` | مقصد نهایی مرورگر خریدار |

**نگهبان راه‌اندازی:** اگر `PAYMENT_GATEWAY=zarinpal` باشد و یکی از این‌ها غلط باشد، سرور بالا
نمی‌آید (`assertGatewaySafety`): نبودِ `ZARINPAL_MERCHANT_ID`، یا آدرس callback/return غیر HTTPS.
پرداخت نیمه‌کاره بدتر از سرویسی است که با پیام روشن بالا نمی‌آید.

تنظیم‌های قابل تغییر از پنل (گروه PAYMENT): `payment.verify_max_attempts` (پیش‌فرض ۳) و
`payment.verify_retry_minutes` (پیش‌فرض ۱۰).

## ۴) گزارش درآمد

`GET /v1/admin/revenue?days=30` (فقط ADMIN/OWNER) → جمع وصول‌شده، تعداد پرداخت، در انتظار، ناموفق،
تفکیک **به تفکیک روش** (درگاه/کارت‌به‌کارت) و **به تفکیک روز**. روزها به وقت تهران بریده می‌شوند
(`AT TIME ZONE 'Asia/Tehran'` در Postgres) تا پرداخت ۲۳:۳۰ به روز خودش تعلق بگیرد؛ اعداد و جداکننده‌ها
هم سمت سرور فارسی می‌شوند.

در پنل، کارت «گزارش درآمد» بالای صفحهٔ پرداخت‌ها همین را نشان می‌دهد، با دکمهٔ
«تلاش دوبارهٔ بررسی درگاه‌ها» که همان مسیر کارگر را دستی اجرا می‌کند
(`POST /v1/admin/reconciliation` → `retriedVerifications` / `verifiedPayments`).

## ۵) داده

مهاجرت `0011_gateway_verify.sql`: سه ستون روی `payments` — `verify_attempts` (پیش‌فرض ۰)،
`next_verify_at`، `last_verify_error` — به‌همراه ایندکس جزئی
`payments_due_verify_idx` روی `next_verify_at` (صف کارگر در هر دور ۳۰ ثانیه خوانده می‌شود).

## ۶) رابط‌ها

- **درگاه:** `GET /v1/payments/gateway/callback` بدون احراز هویت و بدون بدنهٔ JSON؛ هر نتیجه‌ای
  (حتی مرجع ناشناس) با ۳۰۲ به اپ برمی‌گردد، چون این آدرس در مرورگر باز می‌شود، نه در کد.
- **اپ:** صفحهٔ پلن‌ها بر اساس `?payment=` یکی از چهار پیام را نشان می‌دهد: پرداخت انجام شد / انجام نشد
  (با راه پشتیبانی) / در حال بررسی / بازگشت ناشناس.
- **پنل:** کارت گزارش درآمد + دکمهٔ تلاش دوباره.

## ۷) تست

- `apps/api/test/g12-zarinpal.test.ts` (۱۰ تست): مبلغ ریالی و callback در request، پذیرش ۱۰۰ و ۱۰۱،
  تبدیل خطای شبکه به مسیر تلاش مجدد، نگهبان راه‌اندازی، callback عمومی (۳۰۲ + فعال‌سازی + رفرش بی‌اثر)،
  `Status=NOK`، مرجع ناشناس، سه تلاش کارگر و نجات فاکتور، ارتقا به `NEEDS_REVIEW` با اعلان و آدیت و
  تأیید دستی، رد قطعی بدون تلاش مجدد، و گزارش درآمد (تفکیک روش/روز تهران + ۴۰۳ برای کاربر عادی).
- `apps/web/test/g12-gateway-return.test.ts` (۴ تست): پیام هر چهار حالت بازگشت.
- `scripts/smoke-api.mjs`: دو گام تازه — callback بدون توکن ۳۰۲ می‌دهد، و گزارش درآمد فقط برای کارکنان است.
- اثبات مرورگر `pw/g12.mjs`: خرید درگاهی → callback → ۳۰۲ `payment=paid` → فاکتور `PAID` و اشتراک

  «۱۹۶٬۰۰۰ تومان از ۴ پرداخت» با تفکیک هر دو روش + دکمهٔ تلاش دوباره.

### دربارهٔ «کلید واقعی»

برای فعال‌سازی درگاه واقعی فقط این لازم است: `ZARINPAL_MERCHANT_ID` از پنل زرین‌پال در `.env` سرور،
`PAYMENT_GATEWAY=zarinpal`، و دو URL با دامنهٔ HTTPS که به سرور برسند. هیچ تغییر کدی لازم نیست؛
مسیر sandbox (که در این جلسه استفاده شد) و مسیر واقعی یک کد و یک قرارداد هستند.
