# ۰۵ — پرداخت: درگاه بانکی و کارت‌به‌کارت

مالک گفت: «درگاه دردسرش زیاده، کارت‌به‌کارت برایم بهتر است، ولی نمی‌دانم تأیید تراکنش را چطور
بگیرم.» این سند پاسخ دقیق همان سؤال است.

## ۱. خلاصهٔ تحقیق

«کارت‌به‌کارت با تأیید خودکار» یک دستهٔ واقعی و فعال از سرویس‌ها در ایران است. مکانیزم همه‌شان
یکی است و هیچ‌کدام پول را لمس نمی‌کنند:

1. مشتری مبلغ را به کارت خودِ فروشنده (اینجا: کارت مالک) واریز می‌کند.
2. یک **گوشی اندروید در محل شما** پیامک واریز بانک را می‌خواند (اپ همان سرویس یا فوروارد پیامک).
3. سرویس مبلغ را با فاکتور باز تطبیق می‌دهد و پرداخت را در چند ثانیه تأیید می‌کند.
4. نتیجه از طریق API/وب‌هوک به برنامهٔ شما می‌رسد.

سرویس‌های نمونه که همین را ارائه می‌دهند: آبان گیت‌وی [1](https://abangateway.ir/)، پِی زیتو
[2](https://payzito.net/blog/news/card-to-card)، بزن به کارت (با API عمومی، لینک پرداخت و
افزونهٔ ووکامرس) [3](https://bezanbecard.ir/)، و رسیدینو [5](https://residino.com/).

### چطور تطبیق مطمئن می‌شود؟ «مبلغ یکتا»

به‌جای اینکه فقط مبلغ اشتراک (مثلاً ۴۹٬۰۰۰) را بخواهید، برای هر فاکتور یک مبلغ یکتا ساخته می‌شود:

```
مبلغ پلن:        ۴۹٬۰۰۰ تومان
مبلغ یکتای فاکتور: ۴۹٬۰۳۷ تومان      ← ۳۷ تومان «شناسه»
```

کاربر همان ۴۹٬۰۳۷ را واریز می‌کند؛ سیستم فقط با این مبلغ فاکتور را تأیید می‌کند. بزن به کارت هم
دقیقاً همین را توضیح می‌دهد: «مبنای شناسایی هر پرداخت، مبلغی است که فقط برای همان سفارش ساخته
می‌شود» [3](https://bezanbecard.ir/). اختلاف چند تومانی در فاکتور بعدی جبران یا نادیده گرفته
می‌شود (سیاست: زیر ۵٬۰۰۰ تومان نادیده).

### محدودیت‌هایی که باید بدانید

| موضوع | واقعیت |
|---|---|
| نیاز به گوشی | یک گوشی اندروید همیشه‌روشن با سیم‌کارت حساب بانکی مالک لازم است |
| نماد اعتماد | لازم نیست (این خدمات عمداً بدون اینماد کار می‌کنند) [2](https://payzito.net/blog/news/card-to-card) |
| ریسک رسید جعلی | با تطبیق پیامک بانک از بین می‌رود؛ «ملاک، پیامک خود بانک است، نه عکس رسید» [5](https://residino.com/) |
| هزینه | معمولاً اشتراک ماهانهٔ ثابت، نه درصدی |
| محدودیت بانکی | حساب شخصی؛ با رشد تراکنش‌ها ممکن است بانک حساس شود |
| بازگشت پول | باید دستی به همان کارت واریز شود؛ API استرداد وجود ندارد |

مقایسهٔ کلی با درگاه رسمی: درگاه، کارمزد حدود ۱٪ هر تراکنش دارد و به اینماد و کد رهگیری مالیاتی
نیاز دارد [4](https://ensafnews.com/675369/)، ولی برگشت پول و گزارش مالیاتی‌اش تمیزتر است.
برای شروع، کارت‌به‌کارت به‌صرفه‌تر است؛ برای بزرگ شدن، درگاه لازم می‌شود. برنامه باید **هر دو** را
داشته باشد — که خواستهٔ مالک هم همین بود.

## ۲. تصمیم محصولی

هر دو روش با هم، انتخاب روش **از پنل مالک**:

```
settings:
  payment.gateway_enabled        : true|false
  payment.card_to_card_enabled   : true|false
  payment.card_to_card_mode      : "auto" | "review" | "manual"
```

- `auto` — اتصال به سرویس تأیید پیامک (وقتی قرارداد بسته شد)
- `review` — کاربر شمارهٔ پیگیری و ۴ رقم آخر کارت را می‌زند؛ پشتیبانی در صف تأیید می‌کند
- `manual` — آپلود رسید؛ تأیید دستی

اگر هیچ‌کدام فعال نباشد، صفحهٔ اشتراک پیام «پرداخت موقتاً غیرفعال است» می‌دهد (نه خطا).

## ۳. جریان کارت‌به‌کارت (حالت auto)

```
کاربر «پرداخت کارت‌به‌کارت» را می‌زند
      │
      ▼  POST /v1/payments  {plan_id, method:"CARD_TO_CARD"}
سرور: فاکتور با مبلغ یکتا ساخته می‌شود  (status = PENDING, expires 15m)
      │   پاسخ: {amount: 49_037, card: "6037-****-****-1234", holder: "…", invoice_id}
      ▼
UI: کارت بانکی + دکمهٔ «کپی مبلغ» + شمارندهٔ ۱۵ دقیقه + راهنما
      │
      ▼  کاربر واریز می‌کند → سرویس، پیامک بانک را می‌خواند → وب‌هوک
POST /v1/payments/card-to-card/webhook   (امضای HMAC روی body)
      │  تطبیق: مبلغ دقیق + بازهٔ زمانی + فاکتور بازِ همان مبلغ
      ▼
تراکنش: payments.status = PAID, subscriptions فعال/تمدید, audit_log
      │
      ▼  سوکت + پوش: «اشتراکت فعال شد»
```

قواعد پیاده‌سازی:
- وب‌هوک **idempotent** باشد (`event_id` یکتا). پیامک تکراری نباید دو اشتراک بسازد.
- امضای HMAC الزامی؛ در غیر این صورت هر کسی می‌تواند «پرداخت شد» بفرستد.
- اگر مبلغ با هیچ فاکتور بازی نخورد → `payments` با `status = UNMATCHED` + اعلان به پنل، تا
  پول گم نشود.
- انقضای فاکتور ۱۵ دقیقه؛ بعد از آن همان مبلغ به فاکتور جدید داده نمی‌شود (تداخل) — یکتا بودن
  مبلغ تا ۲۴ ساعت رزرو می‌شود.
- مسیر `review`/`manual` هم همان جدول را پر می‌کند و فقط منبع تأییدش `ADMIN` است.

## ۴. جریان درگاه بانکی (زرین‌پال)

نسخهٔ ۱ پیاده است؛ کار باقی‌مانده:

1. `ZARINPAL_MERCHANT_ID` واقعی + `ZARINPAL_BASE_URL` روی `https://payment.zarinpal.com`.
2. `callback_url` با دامنهٔ HTTPS ثابت (بدون آن زرین‌پال تأیید نمی‌کند).
3. تأیید دو مرحله‌ای: `request` → ریدایرکت → `verify` با `authority` و `amount`.
4. آشتی: اگر کاربر از درگاه برگشت ولی `verify` خطا داد، فاکتور در `PENDING` بماند و کارگر
   زمان‌بند بعد از ۳۰ دقیقه `verify` را دوباره تلاش کند (تا ۳ بار).
5. گزارش: مجموع درآمد روز/ماه، تفکیک روش پرداخت، نرخ تبدیل صفحهٔ اشتراک.

## ۵. امنیت و ضدتقلب

- مبلغ و شناسهٔ فاکتور **فقط سرور** تعیین می‌شوند؛ کلاینت هیچ‌گاه مبلغ نمی‌فرستد.
- سقف: حداکثر ۳ فاکتور باز برای هر کاربر.
- تشخیص تکرار: اگر همان ۴ رقم آخر کارت + همان مبلغ در ۱۰ دقیقه دو بار آمد → مشکوک، بررسی دستی.
- شمارهٔ کارت کامل هرگز در اپ یا لاگ چاپ نشود؛ فقط ۴ رقم آخر.
- همهٔ تغییرهای وضعیت پرداخت در `audit_log` با کاربر عامل ثبت شود.
- متن پیامک واریز در لاگ ذخیره نشود (فقط مبلغ، زمان، ۴ رقم آخر).

## ۶. آماده‌سازی سمت مالک (چک‌لیست عملیاتی)

- [ ] یک سیم‌کارت/حساب بانکی مجزا فقط برای دریافت وجه اشتراک
- [ ] یک گوشی اندروید ارزان که همیشه روشن و به برق و اینترنت وصل باشد
- [ ] انتخاب یک سرویس تأیید خودکار و گرفتن کلید API
- [ ] ثبت شمارهٔ کارت و نام صاحب کارت در پنل (قابل ویرایش)
- [ ] تست با ۳ واریز واقعی کوچک و بررسی تطبیق
- [ ] تعیین سیاست اختلاف مبلغ (پیش‌فرض: زیر ۵٬۰۰۰ تومان نادیده)
- [ ] بعد از عبور از ۵۰ تراکنش در ماه: شروع فرآیند اینماد و درگاه رسمی
