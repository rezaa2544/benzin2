# G-09 — کد تحویل ۴ رقمی

**پذیرش:** هنگام MATCHED کد ۴ رقمی ساخته می‌شود؛ فقط خریدار می‌بیند؛ فروشنده با درست زدن کد
وضعیت را COMPLETED می‌کند؛ ۳ تلاش اشتباه → قفل ۱۰ دقیقه + لاگ.

این سند می‌گوید کد کجا ساخته می‌شود، چرا فقط خریدار آن را می‌بیند، و در رابط کاربری هر طرف چه
می‌بیند. مثل بقیهٔ تسک‌های اخیر نصب‌کنندهٔ جدید نمی‌خواهد: از کانال محتوا می‌آید.

## ۱) جریان

1. خریدار آگهی را رزرو می‌کند (`PENDING_OWNER`).
2. صاحب آگهی تأیید می‌کند → رزرو `CONFIRMED` می‌شود و **همان لحظه** کد ۴ رقمی ساخته می‌شود
   (`issueDeliveryCode`). کد تصادفی امن است (`node:crypto.randomBytes`)، نه `Math.random`.
3. خریدار کد را در صفحهٔ معامله می‌بیند (کارت «کد تحویل»، رقم‌های درشت و فارسی).
4. سر جایگاه، خریدار کد را می‌گوید و فروشنده آن را در شیت «تکمیل معامله» وارد می‌کند →
   `POST /v1/reservations/:id/complete` با بدنهٔ `{ code }`.
5. کد درست → `COMPLETED` (مثل قبل: امتیاز، اعلان، آدیت). کد غلط → شمارنده + آدیت، بدون تغییر وضعیت.

## ۲) قرارداد API

```
GET /v1/reservations/:id/delivery-code        (نیازمند ورود، فقط خریدار)
→ { reservationId, orderId, code: "4063", expiresAt, attemptsRemaining, lockedUntil: null }

POST /v1/reservations/:id/complete            { code?: "4063" }
```

- **فقط خریدار** کد را می‌بیند. فروشنده `403 DELIVERY_CODE_BUYER_ONLY` می‌گیرد — اگر او هم می‌دید،
  کل مکانیزم بی‌معنی بود.
- بستن معامله توسط **فروشنده** کد می‌خواهد (`422 DELIVERY_CODE_REQUIRED` اگر خالی باشد). خریدار
  می‌تواند معاملهٔ خودش را بدون کد ببندد (کد دست خودش است).
- کد غلط: `422 DELIVERY_CODE_INVALID` با `details.attemptsRemaining`.
- سه کد غلط: `429 DELIVERY_CODE_LOCKED` با `details.lockedUntil` = حالا + ۱۰ دقیقه.
  تا پایان قفل حتی کد درست هم پذیرفته نمی‌شود.
- کد در بدنه می‌تواند فارسی هم باشد (`۴۰۶۳`)؛ سرور به رقم لاتین تبدیل می‌کند. هر چیزی جز ۴ رقم →
  `422 VALIDATION_ERROR`.

## ۳) داده

- مهاجرت `infra/migrations/0008_delivery_code.sql`: سه ستون روی `reservations` —
  `delivery_code` (text)، `delivery_attempts` (integer، پیش‌فرض ۰)، `delivery_locked_until`
  (timestamptz). در `schema.ts` هم اضافه شده‌اند.
- کد به‌صورت متن ساده ذخیره می‌شود، چون خریدار باید بعداً دوباره بتواند بخواندش؛ عمرش به عمر
  رزرو است، فقط به دو طرف نشان داده می‌شود، و هر تلاش اشتباه آدیت می‌شود.
- رزروهایی که قبل از این نسخه تأیید شده‌اند کد ندارند؛ اولین بار که خوانده یا لازم شوند کد
  ساخته می‌شود (`issueDeliveryCode` ایدمپوتنت است). مهاجرت backfill لازم ندارد.
- آدیت: `delivery.code_rejected` (هر تلاش غلط) و `delivery.code_locked` (تلاش سوم).
  `reservation.completed` حالا `codeVerified: true` را برای بسته‌شدن توسط فروشنده ثبت می‌کند.

## ۴) رابط کاربری

- **خریدار:** کارت «کد تحویل» (`components/DeliveryCodeCard.tsx`) زیر کارت معامله، با رقم‌های درشت
  و LTR، تاریخ انقضا و — اگر قفل باشد — شمارش معکوس دقیقه.
- **فروشنده:** با زدن «تکمیل معامله» شیت تأیید باز می‌شود، ولی این بار یک ورودی ۴ رقمی دارد و دکمهٔ
  تأیید تا کامل شدن کد غیرفعال است (`ConfirmSheet.confirmDisabled`). خطای کد غلط/قفل زیر همان
  صفحه به فارسی نشان داده می‌شود.

### دو باگ واقعی که همین بررسی بیرون کشید

1. **شیت زیر نوار پایین:** کلاس‌های `z-nav` / `z-sheet` / `z-toast` در `tailwind.config.js` تعریف
   نشده بودند، پس به CSS تبدیل نمی‌شدند و شیت تأیید _زیر_ نوار پایین می‌افتاد؛ دکمهٔ تأیید روی
   صفحهٔ گوشی کلیک‌پذیر نبود. حالا `zIndex` از توکن‌های `tokens.css` خوانده می‌شود.
2. **حلقهٔ ورود:** نگهبان مسیر، مقصد را از `window.location` می‌خواند؛ با روت کهنه (StrictMode)
   نتیجه `/login?next=/login?next=/` می‌شد و کاربر بعد از ورود موفق هم روی صفحهٔ ورود می‌ماند.
   حالا مقصد از روت تجزیه‌شده ساخته می‌شود، و اگر سشن در استور باشد ولی هنوز در state نباشد،
   نگهبان اول سشن را برمی‌دارد و کاربر را بیرون نمی‌اندازد.
